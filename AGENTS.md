## 1. Product
AUREM (ORA) — an AI CTO assistant that reads, edits, and ships code
directly into a user's connected GitHub repo via chat.

## 2. Technical Stack
FastAPI 0.115 + Motor 3.6/PyMongo 4.9 + Pydantic 2.10 (backend, `uvicorn`
via supervisor, port 8001) · React 18.3 + Vite 6.4 + Vitest 3.2 (frontend,
port 3000) · MongoDB.

## 3. Repository Structure
- `backend/routers/` — FastAPI endpoints (`/api`-prefixed only)
- `backend/services/` — business logic; `local_tools.py` = ORA's
  read/write/search-repo tool implementations
- `backend/core/` — `intent_gateway.py`, `tool_router.py`,
  `core/parliament/` (multi-perspective review), `boundaries.py`
- `backend/services/actions/pending_action.py` — the confirm/cancel
  state machine (see Architecture Rules)
- `backend/tests/` — pytest; `frontend/src/components/__tests__/` — vitest
- `frontend/src/{components,pages,hooks,lib,services}/`

## 4. Development Commands
- Backend: `sudo supervisorctl restart backend` · tests: `cd backend && python3 -m pytest tests/` · lint: `ruff check backend/`
- Frontend: `cd frontend && yarn test` (vitest run) · `yarn lint` (eslint src) · `yarn build`
- Never run `uvicorn`/`vite` directly — supervisor owns both processes.

## 5. Architecture Rules
- **Vanguard vs. hallucination gate — do not conflate these.** Vanguard
  (`services/vanguard_scanner.py`) is regex-based *security/CVE* review
  (secrets, `eval`/`exec`, SQLi shapes) — nothing else. The
  hallucination/import-preservation gate (`services/cto_pipeline_steps.py`
  + `services/cto_projects_helpers.py`) is *scope-creep* detection: did
  the model silently delete/alter code unrelated to what was asked. They
  run independently and catch different failure classes.
- **Confirmations are deterministic, never an LLM turn.** A "yes"/"go
  ahead" resolving a real pending action (`pending_action.py`) is a
  server-side state transition (`AWAITING_CONFIRM → EXECUTING → VERIFIED`),
  never re-generated by the model.
- **`is_scanner_rule_file()` (`services/scanner_utils.py`)** exempts
  scanner/audit rule-definition files (including vendored skill plugins
  under `.agent/skills/plugins/*/scripts/{scanners,full_audit.py,...}`)
  from self-referential false positives — extend this list, don't
  hand-patch one path at a time.

## 6. Coding Conventions
- Match the existing file's style before introducing a new pattern.
  E.g. every Mongo status transition uses `{"$set": {"status": ..., "resolved_at": _now_utc()}}`
  (`routers/findings.py::resolve_one`) — reuse it, don't invent a new shape.
- No dead scaffolding (unused imports, commented-out code, TODOs in a diff).
- Reuse over reinvent — search `services/` for an existing helper first.
- Comments explain WHY, never WHAT.

## 7. Testing Requirements — current honest state (verified live, not assumed)
- Every bug fix ships with a regression test named
  `test_regression_iter<N>_<description>` (`backend/tests/`).
- **Flaky-test quarantine (Iter 292).** A test that fails intermittently
  with no code change gets `@pytest.mark.flaky(reason="...", owner="...",
  fix_by="...")` — every quarantined test MUST carry an `owner` and a
  `fix_by` date; a flaky test with no owner is a bug in the process, not
  a pass. `pytest.ini` defaults CI to `-m "not flaky"` so quarantine is
  non-blocking. Quarantine ceiling: if `>5%` of the suite is tagged
  `@flaky`, the pattern is systemic — stop quarantining, fix the class
  of failure. Loop/SSE flakiness exception: a flake in async
  Loop/SSE code is not automatically quarantine-eligible — flakes in
  async code often expose a real intermittent bug (an async race, a
  write-visibility lag under load) rather than test noise; root-cause
  before tagging `@flaky`.
- **Frontend behavioural-test rule mirrors the backend one.** A test
  that only greps the DOM/`className` for expected markup (STATIC_GREP)
  is not a valid regression test — render with React Testing Library
  (or drive it with Playwright) and assert real behaviour.
- **Per-environment deploy reporting.** A completion report must state
  whether the change is live on preview vs. live on production — never
  imply "deployed" without saying which. See `docs/environments.md`
  for the current, verified-live surface parity (Mongo, env vars,
  GitHub, services) across preview and production.
- Session start runs `backend/scripts/session_start_dashboard.py` —
  a 3-line, no-ceremony discipline probe (static-vs-behavioural ratio,
  mock-reality check, environment-ledger staleness). Reference it by
  this exact path so a rename doesn't silently strand the discipline.

## 8. Security and Privacy
Never echo a user's GitHub token, API key, or password back in a
response. Per-project GitHub PATs are decrypted server-side only, never
logged. `.env`/`.env.*` files are exempt from secret-scanning (intentional,
gitignored) — do not "fix" by flagging them.

## 9. Generated and Restricted Files
- Test/fixture files are write-blocked by default
  (`local_tools.py::write_repo_file`, `is_test_or_fixture`) — only
  Loop-mode's post-approval commit path may set `allow_test_file_change=True`.
- Top-level imports in an existing file are load-bearing — a real incident
  (`cto_projects_helpers.py`, 2026-09-12) had a "update the footer text"
  edit silently drop 4 context-provider imports from `App.jsx` while
  keeping ~90% of the file intact (invisible to a keep-ratio check).
  Never let an edit tool regenerate a whole file when a targeted change works.

## 10. Verification Requirements
No "fixed" or "verified" claim without live reproduction evidence attached
to the report (screenshot, curl response, real test output) — a passing
unit test with mocked dependencies is not sufficient proof of an
integration point. If a claim says "verified via X," a real call to X
must have happened in that same turn.

## 11. Completion Report
State deployment status via a freshly re-checked `build_hash` (`/api/health`)
— never assume it's current after a restart (`.build_info` can go stale;
see ROADMAP F34). State exactly which parts of a multi-part ticket are
done vs. not; never bundle an unrelated ticket into one report.
