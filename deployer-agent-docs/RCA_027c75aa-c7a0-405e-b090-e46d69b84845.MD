**Deployment:** launch-pad-237 (`https://launch-pad-237.emergent.host`)
**Active run:** 027c75aa-c7a0-405e-b090-e46d69b84845 (redeploy)

## Problem statement
User hit a Cloudflare parse error ("origin returned an empty response / malformed headers / invalid response") while connecting a GitHub repo via the onboarding wizard (POST /api/aurem-dev/cto/projects/add), coinciding with "Deployment initiated" notifications. Reporter suspected a transient rollout blip. Current /api/healthz and / return fast 200s.

## Root cause (what is proven)
After promote at 19:41:55, the newly-live backend pods became **unresponsive for ~14 minutes** (≈19:42–19:57). nginx (:8080) repeatedly timed out reading the response header from the uvicorn backend (127.0.0.1:8001) — the pod accepted connections but returned nothing, i.e. a **blocked/stalled event loop**. This is exactly what surfaces at Cloudflare as "empty / unparseable origin response." Readiness 503 pulled pods out of the Service; liveness 503s fired but the pod was not restarted (restart_count=0) — recovery came only when `-hs6mk` was **preempted** by the scheduler and a fresh pod (`-zjbd4`) came up healthy.

**No OOM** anywhere (no OOMKilled, restart_count=0, graceful exit 0). This was NOT a sub-minute rollout blip — it was a multi-minute backend hang during/after the rollout.

## Correlated contributor (likely, not proven causal)
Throughout the window the app logged `rate_limiter: Redis unavailable at gentle-civet-209255.upstash.io:6379 error=ResponseError: Your database has been temporarily rate-limited` (19:51–20:00), falling back to in-memory. The rate limiter runs in the request path; if its Redis calls block (long/again-and-again timeouts under Upstash rate-limiting) they can stall the single uvicorn event loop, which matches the nginx read-header timeouts. Caveat: these Redis warnings continue after the pod recovered, so Redis rate-limiting alone is not sufficient proof — it is a strong correlated contributor, not a confirmed sole cause.

## Note on the reporter's reproduction
Completed POST /api/aurem-dev/cto/projects/add lines are all `400 Bad Request` (auth_required test traffic) — fast and clean, consistent with the now-healthy pod. The request that threw the Cloudflare error would have hit the hung pod and timed out at nginx before completing, so it does not appear as a finished app response. No nginx upstream-timeout line was found tagged to that exact POST path (logged timeouts are the /health probe path); the POST→empty-response link is inferred from the same backend hang, not directly logged.

## Suggested fixes (NOT applied)
1. CODE (E1): Audit the rate_limiter and any per-request external calls (Redis/outbound HTTP) to guarantee they are async with tight timeouts and cannot block the uvicorn event loop when the dependency is slow/rate-limited. Consider failing open fast. Reproduce under a slow/unreachable Redis.
2. USER / third-party: Upstash Redis is being rate-limited ("temporarily rate-limited, contact support@upstash.com"). Upgrade the Upstash plan or reduce call volume so the limiter dependency stops degrading.
3. PLATFORM: Cluster target-13 showed FailedScheduling (Insufficient memory/cpu, Too many pods) and the stuck pod only cleared via node preemption. Capacity/scheduling pressure on target-13 should be reviewed.
