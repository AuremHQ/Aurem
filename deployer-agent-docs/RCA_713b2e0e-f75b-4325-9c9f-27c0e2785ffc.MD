# RCA — "signin not working" (launch-pad-237)

## Problem statement
User reported "signin not working" on the live app (urgent), with no screenshot/error text, immediately after two back-to-back "deployment initiated" notifications. Login flow was confirmed working in PREVIEW (curl POST 200 + JWT, and full Playwright run to /dashboard). No auth code changes this session.

## Verdict: PRODUCTION IS HEALTHY AND SERVING. Not reproducible on the live URL now.

## Evidence
1. **App reachable**: `GET https://launch-pad-237.emergent.host/` → 200 OK, 620ms, real app HTML (not nginx default). Cloudflare/R2 frontend serving.
2. **Login route up**: `GET /api/aurem-dev/auth/login` → 405 Method Not Allowed (`{"detail":"Method Not Allowed"}`). Expected — login is a POST; a 405 proves the route is registered and the backend is handling requests. No 502/503/504.
3. **Pods healthy**: active run `713b2e0e`, both replicas `Running`, `ready: true`, `restart_count: 0`. No CrashLoopBackOff, no OOMKilled.
4. **Deploy succeeded & promoted**: run `713b2e0e` (redeploy) status=success, completed 03:17:02Z, `active_run_id` == this run. New image (sha256:6318c96…) is the one receiving traffic. No stale revision / no routing split.
5. **Logs clean on auth**: `Application startup complete`, login_attempts/oauth TTL indexes ensured, `init_prod_collections done — errors=0`. Zero 5xx and zero tracebacks on auth/login in the last 20 min.

## Why it matched the timing
The just-completed deploy had a slow image pull (~2m47s) and the new pods only passed the startup probe at ~03:17Z. The `Startup probe failed ... connection refused` warnings are all from the boot window (03:16:25–03:17:05Z) while the app was still starting — normal rollout behavior, not a crash. There was therefore a brief window during the rollout (~03:13–03:17Z) when a user hitting signin could see slowness/failure. Promote committed at 03:17:02Z and the app has been healthy since — which is why it no longer reproduces.

## Secondary finding (non-blocking)
Rate limiter logs show Upstash Redis temporarily rate-limited (`Your database has been temporarily rate-limited, please contact support@upstash.com`). The app logs `falling back to per-process in-memory`, so login still proceeds. This is graceful degradation, NOT the cause of a hard signin failure, but it should be watched — if Upstash stays throttled, rate-limit counts become per-pod/in-memory and inconsistent across the 2 replicas.

## Recommended actions
- Tell the user to retry now (hard refresh / incognito to clear any stale cached JS bundle from before the deploy), and if it still fails, capture the exact error + the failing request in DevTools (status code + response).
- Optionally address the Upstash Redis rate-limiting on the user's Upstash account if rate-limiting behavior matters.
