# RCA — "Deployment failing" report for launch-pad-237 (auremcto.com)

## Verdict
The deployment did NOT fail. The latest run succeeded and the app is live and serving. The pasted "build error logs" are actually a by-design runtime WARNING (graceful degradation), not a build/compile error and not a crash.

## Evidence

### (a) Actual deploy/build status — SUCCEEDED
- `describe_deployment_state`: deployment_status=active, active_run_id=`2c773aa0-f33d-4d2c-b3f7-ad1311e59989`, run_status=success, live at https://launch-pad-237.emergent.host. Custom domains `auremcto.com` and `www.auremcto.com` both verified.
- `get_step_status` (latest run): every step green — wakeup_environment, build, mongodb_migrate, manage_secrets, deploy, health_check all `success`. No failed step. No build error exists.
- `preview_health_check`: GET / → 200, 460ms, real app HTML served.
- The pasted Redis lines are WARNING-level runtime logs from the running pod — unrelated to the pipeline. The pipeline never failed.

### (b) REDIS_URL secret — CONFIGURED; problem is Upstash-side
- `list_secrets` (active run): `REDIS_URL` present and `is_empty=false`. The production secret IS set. This is NOT a missing/blank secret.
- The warning's own text names the real cause: `ResponseError: Your database has been temporarily rate-limited, please contact support@upstash.com` from host `gentle-civet-209255.upstash.io:6379`. That is an Upstash **account/plan-level** rate limit on the Redis database itself — outside the app and outside Emergent. The app connects fine; Upstash is rejecting the commands.
- `fetch_app_logs`: the WARNING repeats ~every 60s (throttled, "N identical warnings suppressed in the last minute"), confirming the app keeps serving and falls back to per-process in-memory rate limiting each time. No exceptions/tracebacks; no boot crash.

### (c) Is the in-memory fallback causing a REAL problem? — Yes, a minor/non-fatal one
- `get_tier`: tier_1 ("Launch"), `replicas=2`, `max_replicas=2`, HPA disabled → **2 pods run concurrently.**
- When Redis is unavailable, rate_limiter.py falls back to a **per-process in-memory** limiter. With 2 replicas there is no shared counter, so:
  - Rate limits are enforced **per pod**, not globally. A client spread across both pods can get up to ~2× the configured allowance, and limits are inconsistent depending on which pod serves the request.
  - This affects the rate-limited paths (e.g. LOGIN_RATE_PER_MIN, SIGNUP_RATE_LIMIT_PER_IP, ORA_CHAT_RATE_LIMIT_PER_HOUR).
- This is degradation, not an outage. It persists only while Upstash is throttling the DB.

## Root cause
The app's Upstash Redis instance is being **temporarily rate-limited by Upstash at the account/plan level**. The app detects this and gracefully falls back to a per-process in-memory rate limiter (by design). Because the app runs 2 replicas, that fallback makes rate limiting looser/inconsistent across pods while Upstash is throttled. The deployment itself is healthy and live.

## Fixes
1. **No code change is required.** The fallback is intentional and the app is serving correctly. Do not treat the WARNING as a deploy failure.
2. **User / third-party action:** Resolve the Upstash rate limit — review the Upstash plan/quota for DB `gentle-civet-209255` and upgrade or contact support@upstash.com. Once Upstash stops throttling, cross-pod Redis-backed rate limiting restores automatically (no redeploy needed).
3. Optional: if consistent global rate limiting during Upstash outages is a hard requirement, that is a design decision for E1 (e.g. provision a more robust Redis / higher Upstash tier) — not a bug fix.
