# RCA — "auremcto.com mobile still shows old view after deploy"

## Verdict
Production is **NOT** serving stale content. The latest deploy is live and current for all user-agents, including mobile. The reported "old mobile view" is a **client-side (on-device) stale service worker / cached app shell** on the specific mobile browser — not a server, CDN/edge, or deploy problem.

## Evidence
1. **Deploy picked up the newest source.** build_image step SUCCESS for run a3126824; build log shows `sw.js` + assets copied to the R2 artifact bucket for this run. Deployed source (inspected in a sandbox built from this run) has `sw.js` at `aurem-v6` (newer than the `aurem-v5` fix from the earlier session) with JS/CSS switched to **network-first**, and `frontend/src/main.jsx` has the `controllerchange` reload-once-on-update logic.
2. **Edge serves the newest sw.js to mobile.** `GET /sw.js` with an iPhone UA on `auremcto.com`, `www.auremcto.com`, and `launch-pad-237.emergent.host` all return `CACHE_VERSION = aurem-v6`.
3. **No separate mobile bundle / no UA divergence.** `GET /` with iPhone UA vs desktop UA returned byte-identical HTML (both 51886 bytes, same `index-GXHYRNkR.js` and `index-DRkxwy_X.css` references, same 9033-byte `#root` SEO snapshot).
4. **Cache headers are correct for cache-busting.** `sw.js`: `no-cache, no-store, must-revalidate, max-age=0`; `/`: `no-cache, no-store, must-revalidate`; `/assets/*` hashed: `public, max-age=31536000, immutable`. Served by Cloudflare worker, `cf-cache-status: None` (not a stale CDN hit).
5. **"ORA by Aurem" is current branding**, not stale — it appears throughout source `frontend/index.html` (`<title>`, meta) and across `src/` pages.

## Root cause
The specific mobile device still has a **previously-registered older service worker** (pre-`aurem-v6`) and/or its cached app shell in local browser storage. The server already serves `aurem-v6` (network-first) with a no-cache `sw.js`, and `main.jsx` reloads once when a new worker takes control — so the fix is live and self-healing. However, on a device that installed an older worker, the browser can serve the old cached shell **once** on the next visit before the new worker finishes install → activate → clients.claim → the one-time reload. On some mobile browsers (notably iOS Safari) the new worker's activation/reload can lag until all tabs of the site are closed and it is reopened.

This is inherent service-worker/browser behavior on the end-user device. There is nothing further the server or a redeploy can change — the edge is already serving the newest build.

## Fixes
- **User / test-and-verify (on the affected mobile device):** Fully close ALL tabs of auremcto.com and reopen, or load it in a private/incognito window, or clear site data for the domain. This forces the new `aurem-v6` worker to activate and will show the current build immediately. Incognito should show fresh content on first load — a quick way to prove the server is current.
- **No code fix required and no redeploy needed** — the `sw.js aurem-v6` (network-first) + `main.jsx` controllerchange reload is the correct durable fix and is already live. (Optional/precautionary only: if iOS Safari users keep reporting a one-load lag, consider surfacing the existing `ora:update-available` event as a visible "refresh to update" banner; this is an enhancement, not the cause.)
