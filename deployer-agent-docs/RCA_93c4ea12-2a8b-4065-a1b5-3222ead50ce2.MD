# RCA — Production (auremcto.com) not reflecting Fix 7/8 "Aurem Loop" auth branding

## Problem statement
After deploy, visiting `/harness` → clicking the waitlist/download CTA → `/signup?next=/harness` (or `/login?next=/harness`) still shows the old "ORA by Aurem" branding instead of the new "Aurem Loop" branding that works in preview. Reporter: "on production didn't change anything."

## Verdict
**This is NOT a deploy-pipeline problem.** The latest deploy succeeded, built the new source, pushed fresh artifacts, and the Cloudflare/R2 edge is serving the new files. Production does not reflect the change because of **client-side service-worker + browser caching serving the OLD JS bundle to returning visitors.** It needs a code fix (SW cache-busting) + a user-side cache clear to verify now.

## Root cause (client-side caching)
`frontend/public/sw.js` is an active PWA service worker that caches static JS/CSS with **stale-while-revalidate**, and purges old caches on `activate` only for keys that do NOT start with `CACHE_VERSION`:
```
const CACHE_VERSION = "aurem-v4";
...
keys.filter((k) => !k.startsWith(CACHE_VERSION)).map((k) => caches.delete(k))
```
`CACHE_VERSION` was **NOT bumped for Fix 7/8 — it is still "aurem-v4"** (the prior Fix 4 deploy already shipped v4). Because the version is unchanged, the activate purge does NOT delete the existing `aurem-v4-static` cache, so a returning visitor's previously-cached app shell / old JS bundle survives and is served via stale-while-revalidate. The SW's own comments document this exact recurring failure mode (sw.js "Fix 4 root cause … serves whatever bundle is already cached on the FIRST request after a deploy"; main.jsx watchdog comment about "stale-index.html-vs-rotated-asset-hash … stuck on the static SEO snapshot baked into #root").

Compounding it: `frontend/src/main.jsx` registers the SW with a plain `navigator.serviceWorker.register("/sw.js")` and has **no `updatefound` / `controllerchange` reload handler** — when a new SW/bundle ships there is no code path that refreshes returning visitors, so they stay on the old SW-controlled content.

Net: the new code is deployed and served by the edge, but returning browsers keep running the old cached bundle. Preview works because it is a fresh origin without the persisted old SW/cache.

## Suggested fixes
1. **Code (E1) — primary:** In `frontend/public/sw.js` bump `CACHE_VERSION` (e.g. `aurem-v5`) so the `activate` handler purges the stale `aurem-v4` caches on next activation. Better/long-term: stop caching content-hashed JS/CSS in the SW (hashed names are already immutable, so caching them stale provides no benefit and causes this), and/or add a `controllerchange`/`updatefound` listener in `main.jsx` that reloads once when a new SW takes control. Redeploy after the change (every future shipped change must bump the version or this recurs).
2. **User (verify now):** To see the fix immediately without waiting for SW turnover — hard refresh (Ctrl/Cmd+Shift+R) or open auremcto.com in a private/incognito window; or unregister the service worker (DevTools → Application → Service Workers → Unregister, then reload). This is a verification step, not the durable fix.

## What was NOT the cause
- Not a failed/partial deploy, not a wrong commit, not a stale container image, not stale R2/edge artifacts (edge serves the new sw.js).
- Not a backend flag/config difference (harness_page_enabled:true, new content served).
