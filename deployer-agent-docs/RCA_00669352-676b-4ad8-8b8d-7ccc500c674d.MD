### 2. Probe timeout vs nginx upstream timeout; resource limits.
This is the smoking gun. The kubelet liveness/readiness/startup probes hit nginx on `:8080/health`, and **nginx proxies `/health` to the backend at `127.0.0.1:8001` with a 1-second timeout**:

```
location = /health {
  proxy_connect_timeout 1s;
  proxy_read_timeout 1s;      # <-- backend must answer /health within 1s
  proxy_send_timeout 1s;
  proxy_pass http://127.0.0.1:8001;
  error_page 502 503 504 = @health_error;   # -> returns 503 to the probe
}
```

So the effective health gate is **1 second**. When the backend event loop stalls for >1s, nginx's `proxy_read_timeout 1s` fires → nginx returns **503** → kubelet records a probe failure. This is exactly the line in your log:
`upstream timed out (110: Connection timed out) ... GET /health ... upstream: "http://127.0.0.1:8001/health"` (observed at 02:32:39, 02:33:08, 02:33:09 on run d80660ad).

Pod events on the live run confirm the consequence:
- `Liveness probe failed: HTTP probe failed with statuscode: 503` (pod `...-rvtjz`, count 12; pod `...-qggzc`, count 7)
- `Readiness probe failed: statuscode 503`
- `Killing ... failed liveness probe, will be restarted` → pod `rvtjz` `restart_count=1` (last_termination Completed/exit 0 — i.e. killed by kubelet, not an app crash).

**Resources (tier_1 "Launch"):** CPU request `250m` / **CPU limit `500m`** (half a core), memory `1Gi` request / `2Gi` limit, 2 replicas, VPA on, HPA off. **No OOMKilled events** anywhere → memory is fine; this is **not** a memory problem. The 500m CPU limit means the single uvicorn event loop can be CPU-throttled during a burst, which lengthens the stall past the 1s /health budget.

## Root cause
The backend's event loop is periodically blocked/starved (multi-second) while handling GitHub App webhook bursts and the associated sequential outbound GitHub API calls / token minting. The `/health` route is proxied to that same backend with a **1s** nginx timeout, so during a stall `/health` returns 503, kubelet fails the liveness probe and restarts the pod. This is a runtime application concern — **not** a build failure, **not** a health-check-step deploy failure, and **not** a memory/OOM issue.

## Recommended fixes (in priority order)
1. **Code (primary, E1/main-agent fix — no infra change needed):**
   - Make `/health` (and the backend `/health` it proxies to) a *trivial, dependency-free, synchronous-fast* route that returns immediately and never awaits shared/GitHub resources. It must be answerable in well under 1s even during a burst.
   - Offload webhook work: return `200` from `POST /github/app/webhook` immediately and push heavy processing (token minting, the outbound GitHub fan-out) to a background task/queue. Do not do the outbound GitHub calls synchronously on the webhook request path.
   - **Cache GitHub App installation access tokens** (they're valid ~1h) instead of calling `POST /app/installations/{id}/access_tokens` repeatedly; move JWT signing off the hot path. Debounce/coalesce the per-webhook polling so a burst of `workflow_job` events doesn't trigger N sequential API sweeps.
2. **Platform/manifest (optional mitigation, stops the pod restarts but masks the stall):** raise nginx `/health` `proxy_read_timeout` above 1s and/or relax the kubelet liveness `timeoutSeconds`/`failureThreshold`. You said no infra changes, so treat this as secondary.
3. **Tier (optional mitigation, not the root cause):** the 500m CPU limit throttles the loop during bursts; a higher-CPU tier would give headroom. No OOM observed, so memory tier is fine. This only softens the symptom — fix #1 is the real cure.
