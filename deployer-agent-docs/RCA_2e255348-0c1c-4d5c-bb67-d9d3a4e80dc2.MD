# RCA — "older homepage still showing on production" (auremcto.com)

## Verdict
**This is NOT a staleness/cache bug. It is case (2): production is correctly serving the LATEST build, which has `VITE_TOKEN_BILLING_MODE` unset → `TOKEN_WORDING_ACTIVE=false` → the intentional legacy task-based copy.** Everything behaves exactly as designed. Showing token copy on prod is a deliberate content change, not a bug fix.

## Answers to the three questions
**Q1 — Is prod serving a stale/cached/pre-migration bundle? → NO.**
- Active run serving production is `2e255348-0c1c-4d5c-bb67-d9d3a4e80dc2` (redeploy, success, completed 2026-11-08 17:03:18Z). Note: this is NEWER than `2c773aa0` referenced in the earlier RCA — there was a subsequent successful deploy. `describe_deployment_state.active_run_id` = this run.
- Both `https://auremcto.com/` and the default `https://launch-pad-237.emergent.host/` serve the IDENTICAL asset hash: `/assets/index-C3JZ4CI2.js` + `/assets/index-DHT7SxS5.css`. No divergent/older edge cache on the custom domain.
- Decisive proof: I fetched the live bundle `index-C3JZ4CI2.js` (756,925 bytes) directly and grepped it. It contains BOTH wording branches as string literals:
  - Token copy present: `Unused tokens carry forward`, `lowest token usage`, `900 tokens`, `tokens / month`, `No per-action billing`.
  - Legacy copy present: `No token meters`, `10 free tasks`, `10 tasks`, `token meter`.
  A pre-migration stale bundle would NOT contain the token strings at all. Their presence proves the live bundle was built from the migrated source (`billingCopy.js` with both branches). The flag simply selects the legacy branch at runtime. (Minified identifiers like `TOKEN_WORDING_ACTIVE` are name-mangled away, as expected; the string literals survive.)

**Q2 — Is it the latest build with the flag off (intentional legacy copy)? → YES.** This is the confirmed state. Verified in the active run's source:
- `frontend/.env.development` → `VITE_TOKEN_BILLING_MODE=on` (dev-only; Vite loads this ONLY for `vite dev`).
- `frontend/.env` → does NOT set it (only `REACT_APP_BACKEND_URL`, `WDS_SOCKET_PORT`, `ENABLE_HEALTH_CHECK`).
- `frontend/.env.production` → does NOT set it (only `VITE_API_URL`, `REACT_APP_BACKEND_URL`).
- No `.env.local` / `.env.production.local`.
- Build command is plain `vite build` (package.json `"build": "vite build && node scripts/seo-prerender.mjs"`; Dockerfile.cloudbuild runs `yarn build`; build-frontend-artifacts.sh runs `yarn build` with no `--mode`). `vite build` defaults to **production** mode, which loads `.env`/`.env.production` but deliberately IGNORES `.env.development`. So the flag never reaches the prod build → `_mode()` falls back to `"off"` → `TOKEN_WORDING_ACTIVE=false`.

**Q3 — Is `VITE_TOKEN_BILLING_MODE` set anywhere in the prod environment/secrets (test or live slot)? → NO.**
- `list_secrets` on the active run returns ~110 keys; `VITE_TOKEN_BILLING_MODE` is NOT among them (no test or live slot exists for it).
- Important: even if it were added as a runtime secret, it would have NO effect. `VITE_*` vars are build-time only — baked into the JS bundle during `vite build`. They are not read from the runtime pod environment. The only place that matters is a file the production `vite build` reads.

## What would actually change prod to token wording (NOT a bug fix — a deliberate content change; confirm with the user first)
Set `VITE_TOKEN_BILLING_MODE=on` in a file the production build reads — i.e. `frontend/.env.production` (or `frontend/.env`), NOT `.env.development` — then redeploy so a fresh `vite build` bakes it in. Note this contradicts the earlier instruction "keep billing mode default off in general, show it on preview only," so it needs an explicit user decision.
