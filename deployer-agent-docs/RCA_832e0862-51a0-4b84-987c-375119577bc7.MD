## QUESTION 1 — write_secrets: ADD-only vs OVERWRITE

**Answer: write_secrets does NOT overwrite a value that already exists in the production Secrets panel. For your own (custom) secrets it is strictly ADD-only — it only fills in keys that are currently missing/unset in production; any key that already carries a production value is left untouched. A preview backend/.env value can therefore NOT silently replace a currently-correct production secret.**

Two distinct buckets govern this:

### Custom keys (the user's own secrets) — ADD-only
Examples in this app: `R2_ACCESS_KEY_ID`, `JWT_SECRET`, `GITHUB_TOKEN`, and every model/API key (`DEEPSEEK_API_KEY`, `OPENROUTER_API_KEY`, `GROQ_API_KEY`, `EMERGENT_LLM_KEY`, `RESEND_API_KEY`, `TAVILY_API_KEY`, etc.).
- On every deploy after the first, custom keys are carried forward from the previous PRODUCTION run. A value you set in the Secrets panel **wins**.
- The preview pod's `backend/.env` only **ADDS keys that production does not already have**. It never overwrites a key that already holds a production value.
- This is exactly the `ENVIRONMENT` mechanism from the prior RCA: `ENVIRONMENT` had **no prior production entry**, so pull_source/write_secrets added it from the preview `.env` (value `preview`). Keys that already had production values were not affected.

### System keys (platform-managed) — regenerated from PRODUCTION state, never from preview
`MONGO_URL`, `DB_NAME`, `REACT_APP_BACKEND_URL`, `INTEGRATION_PROXY_URL`, the Stripe keys (`STRIPE_*`), `EMERGENT_PUSH_KEY`.
- These are regenerated from production state on every deploy and overwrite any preview/user value — **but the source is production state, not the preview .env**. So a preview value can never land in these either.
- Nuance worth knowing before you edit the panel: because system keys are regenerated from production state each deploy, a manual panel edit to `MONGO_URL` or a `STRIPE_*` key may be re-derived/overwritten on the next deploy. Custom keys do not behave this way — your panel edits to custom keys persist.

### Mapping the founder's listed examples
- `STRIPE_API_KEY` → system bucket → from prod state, never preview.
- `MONGO_URL` → system bucket → from prod state, never preview.
- `R2_ACCESS_KEY_ID` → custom → ADD-only, your panel value preserved.
- `JWT_SECRET` → custom → ADD-only, preserved.
- `GITHUB_TOKEN` → custom, but currently **empty** in prod (see below).
- model API keys → custom → ADD-only, all currently non-empty → preserved.

### The only keys still exposed to the ADD path
`list_secrets` on the active run (832e0862) shows these keys currently **empty/unset** in production:
`GITHUB_TOKEN`, `GITHUB_ORG`, `LLM_API_KEY`, `LLM_VISION_API_KEY`, `VERCEL_API_TOKEN`.
Because they have no production value, these are the remaining keys a preview `.env` value could populate on the next deploy (the same way `ENVIRONMENT` was populated). If you want a specific production value for any of them, set it explicitly in the Secrets panel before redeploying. All other keys are non-empty and are safe (ADD-only will not touch them).

**Bottom line for the founder:** your currently-correct production secrets cannot have been silently replaced by preview values. Only previously-unset keys were/are affected — `ENVIRONMENT` already was; the five empty keys above are the only remaining candidates.
