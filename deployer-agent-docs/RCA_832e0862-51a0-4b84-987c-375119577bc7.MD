# RCA — Production `ENVIRONMENT=preview` on job 1b6bb0b1-4adc-4fcf-acd0-64257fdcd80e

## Summary
The production container's `GET /api/health` returns `"env":"preview"` because **`ENVIRONMENT` is set to `preview` as a platform-level Secret/env-var on this production deployment**. It is applied to the running container as a real environment variable at runtime, which the backend reads via `os.getenv("ENVIRONMENT", "production")`. It is **NOT** baked into the Docker image — the user's `.dockerignore` correctly keeps `backend/.env` out of the image, but that is a different code path from secret seeding.

## Q1 — Literal runtime values
- **`ENVIRONMENT` = `preview`** at runtime. Proven two ways: (a) live `GET /api/health` returns `"env":"preview"`; (b) `list_secrets` on the active run shows `ENVIRONMENT` present, `is_empty:false`, and `matches_expected:true` when compared against the expected value `"preview"`.
- **`APP_ENV` = unset.** There is no `APP_ENV` entry in the active run's secret set, so the code falls back to its default (`"production"`). Only the `ENVIRONMENT` name is driving the stamp.

## Q2 — Real mechanism (not a guess)
It is a **platform "Secrets"/env-var panel setting for this production deployment**, injected by the `write_secrets` pipeline step as a container env var — overriding the code's module-level default.
Evidence it is the Secrets panel and NOT a baked image ENV:
- `list_secrets` (active run) lists `ENVIRONMENT` as a stored custom secret with value equal to `preview`.
- No `Dockerfile` manifest override exists for this deployment (`get_deployment_manifest` → `not_found`); the build uses the stock `fastapi_react_mongo_shadcn_base_image` template, which does not set an app-specific `ENVIRONMENT=preview` ENV.
- `.dockerignore` excluding `backend/.env` is correct and effective for image baking, but it has no bearing on secret seeding, which reads the preview pod's environment/`.env` during `pull_source` — a path independent of the Docker build context.

## Q3 — Was there ever a panel entry, and when/how
- **Yes — there is currently a production Secrets entry `ENVIRONMENT=preview`** (confirmed via `list_secrets` on the active run `832e0862`).
- **How it got there (mechanism):** Custom secrets for production are seeded from the preview pod's `backend/.env` on first deploy, and on subsequent deploys the preview `.env` ADDS any keys not already customized in prod. Setting `ENVIRONMENT=preview` in the preview pod's `backend/.env` (to fix the preview health stamp) introduced it as a NEW custom key into the production secret set via `pull_source → write_secrets`. This is why a value you "only set on the dev pod" surfaced in production despite `.dockerignore` — the leak path is secret seeding, not image layers.
- **When / audit trail:** I can confirm the entry is present now and equals `preview`, but I do **not** have visibility into a timestamped audit log of when/by-which-run the panel entry was first written. That part is inferred from the platform secret-seeding model, not directly observed.

## Fix (no changes made — read-only diagnosis)
1. In **Deployment Panel → Secrets**, edit `ENVIRONMENT` to `production` (or delete the key so the code default `"production"` applies), then redeploy. This is a user action; the deployer agent cannot modify production secrets.
2. Going forward, avoid putting `ENVIRONMENT`/`APP_ENV` in the preview pod's `backend/.env`, since custom keys seed/add into production secrets regardless of `.dockerignore`. If the preview pod needs a different stamp, set it in a way that is not carried into the prod secret set.

No `APP_ENV` entry exists, so only `ENVIRONMENT` needs correcting.
