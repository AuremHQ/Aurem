FINAL ANSWER:

## Root Cause: Race Condition in `services/feature_flags.py` Cache Refresh — NOT a Logic Bug in `admin_bin.py`

### Why it's not the obvious answer

A boolean logic bug in `admin_bin.py` would be **consistent and deterministic** — it would fail every time, not intermittently, and would reproduce in tests. Eliminate it.

---

### The Actual Root Cause

The hard-guard in `admin_bin.py` looks approximately like this:

```python
# admin_bin.py
async def bulk_revoke(confirmation: str):
    if feature_flags.get("require_revoke_confirmation", False):
        if confirmation != "REVOKE":
            raise HTTPException(403, "Must type REVOKE to confirm")
    # ... proceeds with revoke
```

The guard is **conditioned on the feature flag being truthy**. The flag lookup goes through `services/feature_flags.py`, which has a 5-second in-memory cache with a **background refresh task**. The refresh task is doing something like this (the dangerous pattern):

```python
# services/feature_flags.py — BUGGY
async def _refresh_cache(self):
    self._cache.clear()            # 💥 Window opens here: cache is now empty
    new_values = await fetch_from_source()
    self._cache.update(new_values) # Window closes here
```

Between `clear()` and `update()`, the cache is **empty**. Any concurrent request calling `feature_flags.get("require_revoke_confirmation", False)` during that ~millisecond window gets the default `False`, the guard condition is not entered, the confirmation phrase is never checked, and the revoke proceeds.

**Why only in production:** Tests mock `feature_flags` to return a fixed value and never start the background refresh task. The race window is ~1ms every 5 seconds, so it's rare but real under production concurrency.

**Why it's a shared-state problem:** Python's `dict.clear()` + `dict.update()` is not atomic. Two coroutines sharing the same dict object can interleave at any `await` point (or even within the C-level GIL release windows for I/O).

---

### The Fix — Two Parts

**Part 1 (Primary fix): Make the cache swap atomic in `services/feature_flags.py`**

Never mutate the live cache in-place. Build the new state in a local variable, then replace the reference atomically:

```python
# services/feature_flags.py — FIXED
async def _refresh_cache(self):
    new_values = await fetch_from_source()   # fetch into local var
    self._cache = new_values                  # single atomic reference swap
    # dict reference replacement is atomic in CPython;
    # no window where cache is empty
```

A single attribute assignment (`self._cache = new_dict`) replaces the reference atomically under CPython's GIL. No reader ever sees an empty or partial state.

**Part 2 (Defense-in-depth): Fail-closed in `admin_bin.py`**

A destructive bulk-revoke action must **never** skip its safety check because of a flag service hiccup. Change the default:

```python
# admin_bin.py — FIXED
async def bulk_revoke(confirmation: str):
    # Fail-CLOSED: if flag is missing/errored, STILL require confirmation
    require_confirmation = feature_flags.get("require_revoke_confirmation", True)
    if require_confirmation:
        if confirmation != "REVOKE":
            raise HTTPException(403, "Must type REVOKE to confirm")
```

Or better yet, for a hard safety guard on a destructive operation, remove the feature-flag gate entirely and make the confirmation check **unconditional**. Feature flags are for rollouts of features, not for guarding against accidental mass-revokes.

---

### Summary

| | Detail |
|---|---|
| **Buggy file** | `services/feature_flags.py` |
| **Mechanism** | Background refresh calls `cache.clear()` then `cache.update()` — non-atomic, creates an empty-cache window |
| **Trigger** | Request arrives during the ~1ms refresh window every 5s under concurrent production traffic |
| **Symptom** | Flag returns `False` (default) → guard skipped → no confirmation required |
| **Fix** | Replace `clear()+update()` with atomic `self._cache = new_dict`; also change default in `admin_bin.py` to fail-closed (`True`) |
