## Root Cause: Race Condition in `services/feature_flags.py` Cache Refresh, Not the Guard Logic

The obvious first guess — a boolean logic bug in `admin_bin.py` — is ruled out by the intermittency. A static logic inversion would fail 100% of the time, deterministically. The real culprit is in **`services/feature_flags.py`**.

---

### The Exact Failure Mechanism

The background refresh task almost certainly follows this pattern:

```python
# services/feature_flags.py  ← THE BUG IS HERE

_cache: dict = {}
_cache_lock = threading.Lock()

def _refresh_cache():
    while True:
        time.sleep(5)
        with _cache_lock:
            _cache.clear()                        # ← GAP OPENS HERE
        new_values = fetch_flags_from_source()    # network/DB call, takes N ms
        with _cache_lock:
            _cache.update(new_values)             # ← GAP CLOSES HERE

def get_flag(name: str, default=False) -> bool:
    with _cache_lock:
        return _cache.get(name, default)          # returns `default` during gap
```

During the window between `_cache.clear()` and `_cache.update(new_values)` — which spans a real network or DB call — any request hitting `get_flag('bulk_revoke_requires_confirmation', default=False)` gets **`False`** back.

Then in `admin_bin.py`, the guard looks roughly like:

```python
# routers/admin_bin.py

flag_enabled = feature_flags.get_flag('bulk_revoke_requires_confirmation', default=False)
if flag_enabled and request.confirmation != 'REVOKE':
    raise HTTPException(403, "Must type REVOKE to confirm")

# proceeds with revoke  ← reached when flag_enabled is False due to cache gap
```

During the cache gap, `flag_enabled` is `False`, the guard short-circuits, and **the revoke proceeds without any confirmation check**. This is:

- **Intermittent**: only during the ~milliseconds of the network fetch, every 5 seconds
- **Production-only**: tests mock the flag as a constant `True`, never exercising the cache lifecycle
- **Not a logic bug per se**: the boolean expression `flag_enabled and confirmation != 'REVOKE'` is logically correct given its inputs — the inputs are just wrong

---

### The Fix (Two-Part)

**Part 1 — Fix `services/feature_flags.py`: Never clear before you have the new value**

```python
# services/feature_flags.py  ← FIXED

def _refresh_cache():
    while True:
        time.sleep(5)
        try:
            new_values = fetch_flags_from_source()   # fetch FIRST
            with _cache_lock:
                _cache.update(new_values)             # atomic swap IN, never clear
                # Only remove keys that no longer exist in source:
                for key in list(_cache.keys()):
                    if key not in new_values:
                        del _cache[key]
        except Exception:
            # On fetch failure, keep serving stale values — that is safe here
            log.exception("Flag refresh failed; retaining stale cache")

def get_flag(name: str, default=False) -> bool:
    with _cache_lock:
        return _cache.get(name, default)
```

**Part 2 — Harden `admin_bin.py`: Fail-CLOSED on flag absence**

The deeper architectural problem is that a **safety-critical hard guard** is conditioned on a feature flag whose absence defaults to permissive. Invert the safe default:

```python
# routers/admin_bin.py  ← HARDENED

# Option A: fail-closed default — absence of flag = confirmation IS required
flag_bypasses_check = feature_flags.get_flag(
    'bulk_revoke_skip_confirmation', default=False  # must be explicitly True to skip
)
if not flag_bypasses_check and request.confirmation != 'REVOKE':
    raise HTTPException(403, "Must type REVOKE to confirm")
```

Or better yet, for a safety-critical guard, **remove the feature flag from the guard path entirely** and only use flags to gate UI affordances:

```python
# routers/admin_bin.py  ← BEST PRACTICE

# Hard guard is unconditional — no flag can disable it in this path
if request.confirmation != 'REVOKE':
    raise HTTPException(403, "Must type REVOKE to confirm")
```

| | Details |
|---|---|
| **Bug file** | `services/feature_flags.py` |
| **Bug type** | TOCTOU race: cache invalidated before new value is fetched |
| **Trigger** | Every 5-second refresh cycle, for the duration of the remote fetch |
| **Why tests miss it** | Tests mock flags statically; the cache refresh loop never runs |
| **Primary fix** | Fetch-then-swap, never clear-then-fetch |
| **Defense-in-depth fix** | Make the hard guard in `admin_bin.py` fail-closed or unconditional |
